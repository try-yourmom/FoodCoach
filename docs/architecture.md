# PlateLens 架构说明

## 1. 设计目标

PlateLens 不是两个互不相关的 Demo。两条管线必须接收同一张图片和同一组用户信息，并转换为可比较的统一结构，否则“并排对比”就会失去意义。

架构遵循三个原则：

1. **事实与估算分离**：识别置信度、边界框、掩膜面积和营养表查值是可追溯信息；克数、热量和模型解释都标为估算。
2. **失败必须显式**：模型加载失败、API 未配置、JSON 无效等情况使用 `status=error/degraded`，不能用模板结果伪装真实推理。
3. **可独立扩展**：传统模型、VLM 供应商和前端互不耦合，后续可替换为训练后的 YOLOv8、GLM-4V 或其他页面。

## 2. 模块划分

```text
Streamlit 页面
   │ multipart/form-data
   ▼
FastAPI /api/v1/assess
   ├── 图片解码与 EXIF 方向修正
   ├── 用户信息 Pydantic 校验
   ├── asyncio.to_thread ──► TraditionalVisionService
   └── asyncio.to_thread ──► VLMService
             │                    │
             └──────┬─────────────┘
                    ▼
            统一 MethodResult
                    ▼
            build_comparison()
                    ▼
             AssessmentBundle
```

API 同时并发两条管线。传统模型加载后缓存在服务实例内，避免每次请求重复加载；VLM 结果按“图片内容 + 用户参数 + 模型和地址”做内存 LRU 缓存。

## 3. 传统视觉管线

### 3.1 检测

- 模型：`yolov8s-worldv2.pt`
- 类别：20 个规范食材类别，展开为 60 个英文提示词变体，检测后映射回规范类别
- 输出：食物类别、置信度、`xyxy` 边界框
- 后处理：默认置信度阈值 0.20；同一食物最多保留两个高置信度框，降低纹理误触发造成的重复计数

### 3.2 分割

- 模型：`mobile_sam.pt`
- 输入提示：YOLO 边界框
- 输出：与图像等尺寸的二值掩膜
- 掩膜面积比例：

```text
mask_area_ratio = 掩膜前景像素数 / 图像总像素数
```

若 SAM 返回的掩膜数量与检测框无法对齐，则降级到边界框面积 × 0.68，并返回警告。

### 3.3 分量估算

单张图片没有深度和真实尺度，因此采用可复现的粗略公式：

```text
餐盘像素覆盖比例 = 0.65（默认假设）
食物面积 / cm² = π × (餐盘直径 / 2)² × mask_area_ratio / 0.65
克数估计 = 食物面积 × 食材参考厚度 × 食材参考密度
输出区间 = 克数估计 × [0.7, 1.3]
```

公式中的 0.65、厚度和密度都是显式假设。最终克数和营养值因此只能解释为粗略区间，不能作为精确称重结果。

### 3.4 营养计算

`nutrition.csv` 提供每 100 克参考值：

- 热量 kcal
- 蛋白质 g
- 碳水 g
- 脂肪 g

计算时按估算克数线性缩放，并保留一位小数。烹饪油和酱汁不在检测类别内，是系统性误差来源。

### 3.5 规则引擎

反馈顺序固定为：

1. 先判事实：热量是否超过单餐参考值、蛋白质是否不足、碳水占比是否偏高
2. 再解释：哪类食物贡献了主要热量
3. 再给动作：下一餐可以直接执行的最小调整
4. 最后提醒：单顿不决定长期结果，但不软化当前事实

热量与蛋白质参考值仅根据体重、目标和本餐情境做教学用简化计算，不代表医学处方。

## 4. 多模态管线

### 4.1 输入

- 原图，最多压缩到 1280 像素长边，JPEG 质量 86
- 身高、体重、可选体脂率
- 减脂 / 增肌 / 维持
- 练前 / 练后 / 非训练日 / 加餐
- 餐盘直径
- 支持的食材列表、反馈原则和固定 JSON 结构

### 4.2 输出校验

1. 去除可能的 Markdown 代码围栏
2. 提取第一个完整 JSON 对象
3. 用 `VLMResponsePayload` 校验字段、长度和数值范围
4. 对不合法归一化边界框直接丢弃，而不是让整次评估失败
5. 计算总营养，并用规则引擎判断整餐事实
6. 检查禁用措辞；命中时替换为安全规则建议并记录警告
7. 检查热量和三大营养素换算是否严重不一致
8. JSON 无效时携带错误信息修复一次；第二次仍失败则返回明确错误

## 5. 统一数据契约

`MethodResult` 同时服务两种方案：

- `method`：`traditional` 或 `vlm`
- `status`：`ok` / `degraded` / `error`
- `foods`：名称、置信度、边界框、掩膜面积、克数区间、营养值
- `totals`：整餐营养合计
- `verdict`：事实判断与摘要
- `advice`：最小可执行动作
- `long_term_note`：长期提醒
- `warnings`：降级或不确定性
- `duration_ms`：该方案耗时
- `overlay_image_base64`：传统方案的框 + 掩膜可视化
- `metadata`：目标参考值、模型、设备、尝试次数等

## 6. 对比逻辑

对比不是单纯比较两段文字，而是生成结构化维度：

- 食物名称集合及重合度
- 是否有掩膜和可复核定位
- 总热量差异及百分比
- 情境反馈方式
- 运行耗时
- 单次成本
- 可解释性与平均置信度

最终结论不预设“大模型一定更好”。传统方案适合固定菜单、可解释定位和批量处理；大模型适合开放菜品、混合菜和自然语言解释。
