## 1. 我做了什么

本次项目是 FoodCoach 的单餐视觉评估切片 PlateLens。它接收一张餐盘图片，同时运行两种方案：

- 传统方案使用 YOLO-World 检测食物，用 MobileSAM 根据检测框生成掩膜，再通过面积、食物厚度和密度估算分量，查询本地营养表并由规则引擎生成反馈。
- 多模态方案把图片、用户信息和自己拍摄或选择的餐盘场景发送给 Qwen3.8-Omni-Flash，要求返回固定 JSON，并在服务端做结构校验和重试。

前端使用 Streamlit 并排展示两种结果，下方给出食物重合度、热量差异、定位能力、速度、成本和可解释性的比较。

## 2. 我对两种方案的理解

传统模型给我最直观的感受是“可控”。每个结果都能追溯到检测框、掩膜、营养表和公式。模型漏检时，我也能通过 bbox 和掩膜看出它错在哪里。

大模型的优势是理解开放场景和自然语言。面对混合菜、陌生菜名或复杂情境，它比固定类别检测器灵活。但营养数值并不天然可信，同样一张图可能给出不同的克数。通过 JSON 校验和警告机制，我更加理解了“生成结果的流畅”不等于“结果正确”。

## 3. 遇到的问题

### 问题一：普通 YOLO 不认识足够多的健身食材

COCO 预训练类别只有少量食物。最终选择 YOLO-World 零样本文本提示，避免在短时间内伪造一个“训练好的检测器”。这也让我接受了项目的一个重要局限：它能完成课程切片，但不等于成熟产品。

### 问题二：单张图片无法真正称重

最初很容易把分割面积直接当作克数，但图片没有深度和尺度。最终把餐盘直径、面积占比、食材厚度和密度都写入公式，并输出区间和警告，而不是输出一个看似精确的数字。

### 问题三：大模型可能返回不合法 JSON

解决方案是固定提示词结构、解析代码围栏、Pydantic 校验和一次修复重试。如果仍然失败，就明确展示错误，不生成假结果。

## 5. AI 辅助开发说明

本项目使用 AI 辅助完成代码骨架、接口设计、测试和文档初稿。AI 提高了开发速度，但需要人工完成以下判断：

- 选择哪些食材进入支持列表
- 营养表是否合理
- 两条管线能否公平比较
- 失败时是否应该展示错误而不是编造结果
- 哪些表述可能制造身材焦虑
